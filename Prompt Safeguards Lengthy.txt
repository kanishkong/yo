## Strict anti-overengineering rules

Follow these constraints carefully:

1. Include only technologies that are genuinely necessary or highly valuable for an SDE1/SWE1 Java backend role.
2. Every included technology must solve a specific project requirement.
3. Explain why each technology is included and what problem it solves.
4. Prefer mastering a small, focused stack over gaining shallow exposure to many tools.
5. Use a well-structured modular monolith by default.
6. Do not introduce microservices unless there is a compelling requirement that cannot be handled reasonably by a modular monolith.
7. Do not add Kafka, Kubernetes, Redis, Elasticsearch, NoSQL, GraphQL, gRPC, service meshes, multiple databases, or multiple cloud services merely to make the project appear advanced.
8. If one of these technologies could be useful but is not necessary, place it under an optional “Learn Later” section.
9. Do not turn the Level 4 project into an enterprise-scale distributed system.
10. Do not create an enormous feature list that a beginner cannot complete or explain properly.
11. Do not add a frontend framework unless a minimal frontend is genuinely necessary. The main focus must remain backend engineering.
12. Prefer relational database design unless the project has a clear and justified need for another database type.
13. Do not include a technology just because the named companies use it. Include it only if it teaches a transferable entry-level engineering skill.
14. Do not use artificial performance claims such as “supports millions of users” unless the project actually includes reproducible testing and evidence.
15. Clearly distinguish between:
    - Essential for the project
    - Useful but optional
    - Premature or unnecessary for an SDE1 learner
